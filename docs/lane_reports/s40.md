## Reproduction and dependency handling

Commands below are the exact normal promote invocations in dependency order. They intentionally omit publication. Dependent commands cannot pass against the unchanged current database: their predecessor identities must first be integrated by the integrator. The current-state refusals are saved separately. `diagnose.py` projects the predecessor symbol changes **only in memory**, calls the unmodified promote dry run for the dependent candidate, and checks the comparator view without --at/search after each proposed step. It never saves symbols or an acceptance ledger. Its output is `build/s40/diagnose.txt` and the `*.post.json` comparisons.

To repeat the read-only diagnostic chain:

```powershell
python candidates/s40/diagnose.py
python candidates/s40/sinterp_evidence.py
python candidates/s40/audit_aliases.py
```

The scratch-confinement launcher `run_tool.py` invokes the repository tools and redirects their build-root temporary directories to build/s40. It sets cc's scratch directory there too. Because symbols.scope_of_module recognizes the literal build/cc path, the launcher translates **only that scratch path component** from build/s40/cc to build/cc when extracting TU scope. Without this path accommodation, a logic/sinterp.c compile would falsely acquire scope sinterp.c. Comparator rules, bindings, policy, oracle, flags, and source are otherwise unchanged. All comparator JSON receipts used for conclusions use the correct scope. An initial direct comparison with the lane scratch path was superseded.

## 1. GuiPoint and tdisplay: correct destructor identity; filler-size caveat

The work order and blocked note misidentify 0042c9d0 as a constructor. The original s21 REPORT.md correctly identifies it as a **destructor**. The oracle descriptor at **0048daa4** is:

```text
00 3c9a4200 049a4200 d0c94200 08000000
   ctor       copy       dtor      sizeof=8
```

Thus the true shared identities are:

| VA | Identity / mangled name | Evidence |
|---|---|---|
| 00429a3c | GuiPoint::$ct / W?$ct:GuiPoint$n()_ | Descriptor constructor slot; s21 default constructor is 5 bytes STRICT |
| 00429a04 | GuiPoint::$ct / W?$ct:GuiPoint$n(rnx$0$)_ | Descriptor copy slot; s21 native copy constructor is 21 bytes STRICT |
| 0042c9d0 | GuiPoint::$dt / W?$dt:GuiPoint$n()_ | Descriptor destructor slot; explicit inline empty destructor in tdisplay is 16 bytes STRICT |

`candidates/s40/terr/tdisplay.c` replaces the working GridPoint class with GuiPoint (two longs), uses its native constructors, and declares the inline empty destructor. No machine bytes or runtime-internal calls were introduced. Both constructor overloads are anchored by **exact mangled name**; readable `GuiPoint::$ct` would incorrectly place both at one VA.

Two additional conflicts appear once the first is removed. Descriptor **0048daf4** is:

```text
00 f0c94200 08e04700 e0c94200 10000000
   ctor       copy       dtor      sizeof=16
```

It identifies DisplayIdentityB as DisplayRenderItem's implicit destructor at 0042c9e0 and DisplayIdentityC as its default constructor at 0042c9f0. Both wrappers were replaced by the real constructs. The implicit destructor remains STRICT for 16 bytes. The inline constructor emits 5 bytes STRICT plus `tail_fill=11`, rather than a 16-byte ordinary-function extent. The empty explicit destructor variant also shortened the destructor to 5 bytes; the delivered source keeps the implicit destructor to preserve its full 16-byte claim. Non-inline constructor/destructor experiments lost fn_init and _DATA and were rejected. Two further natural constructor spellings, explicit `: point()` initialization and an in-class empty body, both compile STRICT to the same 5-byte extent with tail_fill=11 (`build/s40/member_init.json`, `in_class.json`); neither preserves the old padding count.

All other 18 original accepted functions retain their original VA, size and STRICT verdict. DisplayIdentityA and B retain 16-byte STRICT extents under their new identities; C retains its full 5-byte body but loses the 11-byte counted padding claim. The old GridPoint typesig is replaced by the byte-identical GuiPoint typesig at 0048daa4. All other recorded data segments remain STRICT. The required --accept-loss arguments are narrowly listed renames/data-key replacement; **DisplayIdentityC also carries the disclosed padding loss**. No acceptance-loss option was used to admit a DIFF body.

## 2. MCI: split the accidentally aggregated resource owner

Decision: **0047d0e0..0047d400 is a separate original object**, with no surviving path evidence, so it belongs to src/_unknown/tu_0047d0e0.c. Resource owns 0047c530..0047d0e0. The heuristic module combines them because both objects are aligned and there is no zero gap. Resource's final RenderFormattedResourceText returns at 0047d0df; the next byte is the module-registration initializer at 0047d0e0. A real global MciState compiles its initializer first, independent of source declaration order. Its 48 bytes and real CONST2/_DATA registration records are STRICT in the separate object. A middle-of-resource initializer is incompatible with that compiler ordering; the io/resource.c assertion path occurs in the preceding resource region, not the MCI methods. This corroborates s29's split evidence.

The six MCI extents were accidentally counted by src/io/resource.c. `symbols.py show 47d110` reports f_d110 matched there. The initializer calls 0047d110 to initialize gShellResources at 00513958; it zeros device/pending/state and returns this. The module registration record's destructor target is 0047d130. Therefore f_d110 is **MciState::MciState()**, and the returning-this StopClose wrapper is **MciState::~MciState()**. The delivered standalone candidate uses those actual C++ definitions and gShellResources, with no invented constructor forwarding function or name barrier.

`candidates/s40/io/resource.c` removes the MCI class/global/methods, preserving resource assertion line numbers. It retains all 16 resource STRICT functions and the ResourceEntry descriptor. The six accepted-loss options below transfer ownership; the following standalone promotion re-proves all six at the same VAs and sizes, plus the initializer. ## 3. sinterp: exact rollback cause is an incorrectly recorded BSS address

Reproduced original dry run:

```powershell
python tools/cc.py --profile plain-oe --as 'logic\sinterp.c' candidates/s40/logic/sinterp.c '-fo=build/s40/sinterp.obj'
python tools/compare.py build/s40/sinterp.obj -v
python tools/compare.py build/s40/sinterp.obj --at 'W?.fn_init$n()v=46794c' --at ScriptFree=46799a --find --imply -v
python tools/promote.py candidates/s40/logic/sinterp.c --tu src/logic/sinterp.c --as 'logic\sinterp.c' --profile plain-oe --at 'W?.fn_init$n()v=46794c' --at ScriptFree=46799a
```

The lane launcher was used for the actual confined executions. Correct-scope receipts: sinterp.verify.json/txt, sinterp.dry.json/txt, sinterp.promote.txt.

```text
src/logic/sinterp.c: 18 strict functions (2107 bytes), new 3, lost 0
dry run OK (add --publish to accept)
```

Before any projected publication, plain comparison has ScriptLoad STRICT at 00467a86, while ScriptString is UNPLACED. The dry-run view finds ScriptString at 00469c41 and explicitly anchors ScriptFree. Those placement differences explain the gain but **do not cause the rollback**. ScriptFormat remains bound to 00469a95 in both views; MissionRandomTable#W?MissionRandomTable$nui stays at 0051445c. Neither changes in the failing replay.

The actual divergence:

1. The object has BSS publics in order: local ScriptRef::result +0, its guard +8, local scriptText +0xc, gScript +0x80c. Its bound gScript=004f30b4 implies BSS base **004f28a8**. This candidate does not reproduce the original BSS order. Oracle instructions independently place scriptText at **004f28a8**, ScriptRef::result at **004f30a8**, its guard at **004f30b0**, and gScript at **004f30b4**.
2. The existing unscoped binding `scriptText`, mangled `W?scriptText$n[]a`, is correctly **004f28a8**. During dry comparison its references resolve through that exact-mangled extern binding; byte checks of the zeroed object succeed, so ScriptLoad and ScriptString are STRICT.
3. promote.py's own-data placement loop records every public in a placed BSS segment. It computes base+0xc and adds a NEW scoped key `scriptText@logic/sinterp.c` at **004f28b4**, with the **same exact mangled name**. The analogous result/guard additions are also at wrong addresses. No source or flag changes are needed to trigger it.
4. symbols.Resolver.__init__ constructs `by_mangled` with a dictionary comprehension. Two keys now have the same mangled name and different VAs. After symbols.save sorts entries by VA, the new scoped 004f28b4 entry wins over 004f28a8. An extern reference, resolved without local scope, now returns the wrong address. The post-publication compile therefore differs at nine ScriptLoad relocations and three ScriptString relocations.

`diagnose.py` replays these symbol additions only in memory; `sinterp.post.json` exactly reproduces:

```text
sinterp post-view failures: [('ScriptLoad', '00467a86', 718, 'DIFF', 9), ('ScriptString', '00469c41', 55, 'DIFF', 3)]
```

The relocation fields change **004f28a8 -> 004f28b4**; the oracle retains 004f28a8. Exact field sites (`sinterp.fields.txt`):

```text
ScriptLoad:   00467c3d 00467c4e 00467c56 00467c9e 00467caf 00467cba 00467d00 00467d11 00467d1c
ScriptString: 00469c5c 00469c6d 00469c72
```

The first differing byte in each field is a8 vs b4. Both addresses are zero in the oracle, which is why checking BSS bytes alone cannot prove placement or disambiguate identity. This is a promotion/resolver bookkeeping defect exposed by an incompletely reconstructed BSS layout, not a masked-byte or unbound-callee problem.

Integrator fix direction (not implemented in this lane): reconcile own-public placements with all existing exact-mangled/reference evidence before recording them; a placed BSS segment with inconsistent item evidence is insufficient to publish every item at base+offset. Resolve duplicate exact-mangled entries with conflicting VAs explicitly, rather than silently choosing dictionary order. Retaining the independently correct scriptText binding is necessary, but a skip-existing-name special case alone would leave result/guard addresses unjustified. Preserve strict per-item/zero-byte checks and the post-publication rollback. A source rewrite changing static storage/linkage merely to avoid the scoped key would conceal the problem and lacks original-source evidence; none is proposed. The s40 sinterp source is otherwise the s28 candidate and is **not publication-ready** until the tool records consistent identities or the actual BSS order is recovered.

## 4. Exhaustive alias inventory and other point TUs

`build/s40/aliases.txt` saves symbols.py aliases output. **ALIASES.md** lists every function VA having multiple symbol keys and a STRICT accepted owner, with all names, exact ledger-owned mangling/size, the name to use (or stated historical-name uncertainty), evidence, and candidate users. `build/s40/aliases.audit.json` is its machine-readable evidence index, not an acceptance ledger. The directly proven additional constructor/destructor debt includes DisplayRenderItem's B/C aliases above, ActorCloseRecord/ActorRecord::$ct at 00456c80 (already assigned elsewhere; typesig/member-construction evidence in docs/blocked.md), and FileInit/FileRecord::$ct plus FileRecord::Release/FileRecord::$dt at 0047e450/0047e470 (real ResMgr member construction/destruction). The latter are relevant to resource candidates but no additional gain was measured. The exhaustive table distinguishes these from ordinary descriptive aliases and exact-mangled prototype variants; it does not pretend to recover historical identifiers from equal machine code.

No other alias was promoted or rewritten, and no excluded active-lane TU was built. GUIPOINT.md records the source review, including other GridPoint spellings whose class identities cannot be settled by equal two-word layout alone.
