# Lane r3: register and stack allocation research

STATUS: partial

The deliverable is an executable **restricted predictive model**, source-backed decision procedure, and measured limits. **No new STRICT candidate was obtained.** The model predicts 174/174 register homes and 18/18 stack layouts in its stated straight-line domain. Four parked targets in four published TUs were investigated; 14 full-TU experiments produced no protected gain. Ten promotion dry runs pass with new 0/lost 0; four reject accepted-function losses. Those rejected experiments are research evidence, not integration proposals.

The important correction to the previous search strategy is that there is no single variable-order rule. Backend name creation, conflict discovery, benefit sorting, register affinity, previously assigned registers, and final physical-register optimization are separate stages. Equal benefit is **not** broken by a conflict ID comparison. The normal list sort is not stable. Declaration order matters demonstrably for some stack objects and is ineffective in the measured scalar-register controls.

Only `candidates/r3/` and `build/r3/` were authored. No publication, canonical source/tool/config/doc/ledger edit, git operation, network operation, oracle execution/modification, or background process was performed. The tools use their normal pinned oracle checks for comparisons. No assembly, fabricated storage, copied code bytes, volatile hints, artificial register pragmas, or padding was introduced. ## 1. Front-end locals and backend temporary creation

1. **Ordinary locals are declared eagerly when their scope opens.** `plusplus/c/cgbkmain.c:2364` handles `IC_BLOCK_OPEN` by `ScopeWalkOrderedSymbols(scope, CgDeclSym)`. `scope.c:1472` walks the ordered ring; `addOrdered` at 1823 appends symbols in insertion order. `cgbkdecl.c:212` calls `CGAutoDecl`, including both AUTO and REGISTER symbols in `CgDeclSym`. The ordinary named-local path is consequently not “create a temp at first textual use.” Expression-generated and anonymous symbols have additional filtering; do not extend this statement to every frontend temporary.
2. `cg/c/bldcall.c:164` (`BGAutoDecl`) creates the backend name through `MakeAddrName`; `makeaddr.c:586` uses `SAllocUserTemp`. `namelist.c:507` consults the symbol's existing back handle before allocating. `SAllocTemp` at 472 gives the new master `++TempId`; `AllocName` at 85 prepends it to `Names[N_TEMP]`. Aliases at `STempOffset:418` share the master ID. Thus declaration order, name-list order, and alias order are different things.
3. **An expression does not necessarily create a persistent new temporary.** `bldins.c:193` (`CnvRnd`) calls `Unary` only if `NeedConvert` says a conversion is needed; otherwise it may demote an address or merely change its type. `Unary:179` obtains the operand with `GenIns` and makes an instruction; later address materialization creates the result name. `makeaddr.c:371` (`Convert`) explicitly creates an ADD temp if there is a pending offset and then a conversion temp. A same-width cast is therefore not a guaranteed ID lever. No claim that an arbitrary cast temp is always before/after the named destination survives these paths.
4. `tree.c:1875` (`TNPostGets`) materializes the old value into a new temp for a used postfix result. `TNPreGets:1899` has a different path. Whether those names survive propagation is another question. The old “compound vs explicit” negatives remain applicable.
5. **Inline expansion has its own names.** `plusplus/c/cgbkdecl.c:70` translates non-static inline locals to fresh symbols. `cg/c/inline.c:141` (`BGParmInline`) allocates the inline parameter and emits a MOV from its argument. `BGRetInline:162` creates a result temp and assignment for a non-void result. `tree.c:2295` (`TNCall`) processes arguments and has further temps for special argument forms. These boundaries explain why flattening an inline body is not guaranteed to preserve the conflict graph. They do not supply a universal original-source spelling.

Measured controls: reversing two scalar declarations and moving the second scalar to a nested scope are byte-identical to the 34-byte baseline; reversing equal-size array declarations changes their stack addresses. Inline pure-load getters and same-width int/long casts collapse to the same baseline bytes. Genuine narrowing captures the two values in BL/BH across a call and inserts widening on output (38 versus 34 bytes).

## 2. Conflict creation, traversal, and benefit

1. Pre-optimization runs before allocation (`cg/c/generate.c:147`, `PreOptimize`): dead-temp removal, flow construction, common expressions/conversions, propagation, loop processing where enabled, etc. Raw source reference counts are not the allocator's reference counts.
2. `dataflo.c:98` (`RoughSortTemps`) first creates nodes for eligible cross-block temps, adds `Weight(1, block)` for operands/results, and sorts the temp list. `AllocBefore:72` puts constant temps last, conflicted temps first and orders their **rough** savings descending; only the no-conflict fallback compares descending temp IDs. This rough sort helps when global liveness bits run out. It is not the final register-benefit sort.
3. `MakeConflicts:203` assigns global bits to temps before memory. Lack of a global bit can defer a temp (`CST_CONFLICT_ON_HOLD`); bit shortage is not automatically a permanent spill of every such value.
4. `liveinfo.c:347` (`MakeLiveInfo`) puts global conflicts first, renumbers instructions, then visits blocks forward. `FlowConflicts:217` scans instructions backward inside each block, visits operands in increasing operand order, and processes definitions and zap sets while moving backward. `conflict.c:49` (`AddConflictNode`) **prepends** each new node. `FindConflictNode:155` de-aliases and finds/extends the appropriate range, or creates another local range. Its IDs are liveness bit sets, not a compared priority number.
5. For the restricted single-block independent-load/store family, these paths yield initial conflict-list order by **ascending final-use position**. Changing only load order leaves the homes unchanged; changing final-store order exchanges equal-cost homes. Once other blocks, global conflicts, generated names or reductions exist, this shortcut is no longer established.
6. `regalloc.c:1214` (`AssignConflicts`) calculates missing savings, adjusts constants, and sorts conflicts using `ConfBefore:1196`, whose entire comparison is `c1->savings > c2->savings`. Zero-benefit/uncacheable conflicts go to memory; other conflicts get a register attempt. The iterative expansion/allocation loop at `RegAlloc:1303` can create more work and repeat; this is not a one-shot coloring by source variables.

The real benefit is calculated by `regsave.c:121` (`CalcSavings`) and the included `cg/h/savcode.h:84` onward. Operand uses, definitions and index uses add savings; necessary loads/stores add cost. There are bonuses for certain already-register operands/results. Cross-block memory/address-exposed values can incur synchronization around calls and block boundaries. A conflict with first==last is assigned zero savings by this path. Savings saturate below `MAX_SAVE`, except specially forced cases.

`intel/c/x86regsv.c:48` (`InitWeights`) combines size/time costs by target CPU. For CPU 486, uses/definitions/push/pop have unit base costs; load/store are `COST(3,1)`. `regsave.c:61` computes loop weight as `max(1, 20*time/256)` and powers it through depth five; `Weight:109` applies it with depth capped at five. OW's frontend `plusplus/c/cmdlnany.c:766` supplies size percentage 50 by default and 0 for -ot. This predicts **loop factor 10 / load cost 2 in plain**, versus **loop factor 20 / load cost 1 in ot** on the 486.

These are more than qualitative predictions. `loop_threshold.py` compares one loop use of a against N distinct outside stores of b. For N=7,9,10,11,19,20,21,24, the historical compiler puts a in EBX through N=10 in plain and N=20 in ot; it switches to b at N=11 and N=21 respectively. All 14 non-tie directional predictions agree; at both predicted ties a wins. This supports the predicted numerical first-depth ranking, without uniquely proving the historical frontend's internal percentage or higher-depth formula. `index_priority.py` then distinguishes the load/index cost: a pointer used once as an index competes with a once-used scalar whose final store comes first. Plain gives pointer EBX (predicted benefit 1+2 versus 1+1); ot gives scalar EBX (benefits tie, scalar final-use first). Both predictions agree. The point-load intermediate itself ends up differently after allocation, so this is a home-ranking claim, not complete instruction prediction.

### Equal savings: the actual tie mechanism

`cg/c/cgsrtlst.c:169` (`SortList`) normally materializes an array and calls `ShellSort:138`. Its gaps are generated by alternately halving with/without an extra one; it swaps separated entries only on strict `before` comparisons. Equal entries never directly swap, but other entries can move past them, so the result is **not stable**. For example, input benefits `[a:1,b:1,c:2,d:0]` become `[c:2,b:1,a:1,d:0]`. The model includes this exact sort and predicts the non-obvious equal-benefit reorder in the five-value weighted controls.

The allocation-failure fallback uses `MergeList:64`, which takes the second list when `before` is false, including ties. That path is visibly different. It was **not induced or tested** in 10.6; do not use memory pressure as a source reconstruction technique.

There is no universal “lower temp/conflict ID wins” or “first referenced local wins” rule in this implementation. An ID can affect an earlier list order, which then passes through several sorts and prepends. It is not a final numeric tie break.

## 3. Which register gets a value

`regalloc.c:925` (`GiveBestReg`) calls `NeighboursUse:793`, which accumulates physical-register interference across the live range, including instruction zap sets. Copy-related equivalences can avoid some otherwise conservative interference. It then traverses the legal register alternatives from the register tree (`regtree.c:163`, `BuildPossible`; `BuildRegTree:503`).

For each legal alternative:

1. Exclude interference and `CurrProc->state.unalterable` (ESP, and frame registers when required).
2. `TooGreedy:707` refuses to take the last register still reserved for an unexpanded instruction, index or segment operand. It can postpone/split an index requirement instead of immediately accepting an impossible assignment.
3. Rank remaining registers by `CountRegMoves:416`: full eliminated MOVs score `tree->size`; usable in-place binary operations and overlapping-register conversions generally score half that. This score is separate from the loop-weighted memory benefit. It favors an instruction's source/destination affinity, not a global EAX-first policy.
4. At equal move scores, prefer a register already in **GivenRegisters**, the function's accumulated assignments; otherwise retain the earlier legal table entry. This set is not “the live registers at this instant.” `given_reuse` demonstrates a later non-call-crossing value using EBX after an earlier EBX owner dies, avoiding another saved register.
5. Unless a register is compulsory for a split, `WorthProlog` (`intel/c/x86regsv.c:96`) compares benefit with any newly incurred push/pop cost. Already-given registers and registers that need no callee save have zero additional prologue cost. Constant caching has additional adjustments. Failure can send every conflict for the name to memory (`InMemory`, `regalloc.c:1113`) or leave a needed index split for another iteration.

There is also a conditional `CGSW_GEN_SUPER_OPTIMAL` branch in `CountRegMoves:539`: it considers register parts, adds a preference for registers outside MustSaveRegs, and can follow intermediate MOV-connected conflicts recursively (initial depth three). The inspected frontend enables it with -oh (`cmdlnany.c:1000`), separately from -ox. It was not enabled as a new flag experiment here; its exact historical availability/behavior is not measured by this lane. It should not silently be included in an unconditional plain/ot prediction.

The model's measured **10.6** register order for independent, equal-cost dword values is:

| Constraint context | Measured order / effect |
|---|---|
| Leaf; up to seven simultaneous dwords | EAX, EDX, **EBX**, ECX, ESI, EDI, EBP |
| Values live across the external `barrier()` | EBX, ESI, EDI, EBP; a fifth value uses a four-byte stack slot |
| Three independent bytes in a leaf | AL, AH, DL; the source table continues DH, BL, BH, CL, CH (that full continuation was not independently tested) |
| Two unsigned bytes live across the call | BL, BH; then zero-extension for dword stores |
| Three independent words | AX, DX, BX |
| Variable shift | ECX/CL count, EAX result in the probe |
| Signed division | EDX:EAX dividend, EAX quotient; plain uses memory divisor, ot loads divisor into EBX |

**OW/10.6 boundary:** OW's `intel/386/c/386rgtbl.c:288` `DoubleRegs` puts **ECX before EBX**, whereas the 10.6 leaf controls use EBX before ECX and even save EBX despite unused ECX. Its `ABCDRegs:281` and `DoubleParmRegs:299` have EBX before ECX. `regtree.c:175` preserves the chosen register-list order. Thus a naive substitution of today's `DoubleRegs` as the historical unconditional preference is contradicted. These experiments establish the historical output order in this domain; they do **not** identify whether the original difference is the table, the selected restriction list, or another reduction/ranking detail. No OW compiler was built or substituted, and no byte-level divergence of its internal allocator was directly observed.

One frontend version boundary is more concrete: current OW -ox calls `CgBackSetOeSize(20)` (`cmdlnany.c:748`), while historical 10.6 -ox does not imply general same-TU expansion. The new `profile_control.py` has a tiny non-inline helper: plain and ot retain one call, ot-oe eliminates it. This freshly corroborates the repository's existing -oe rule. Do not infer original inline-name creation from the descendant's -ox option bundle.

## 4. Stack assignment and reuse

`cg/c/temps.c:680` (`AssignTemps`) first propagates aggregate flags and existing parameter storage, tries push-initialized locals, then calls `AssignOtherLocals:481`. The latter sorts the current temp list by target `TempAllocBefore` and assigns still-needed unassigned masters. `intel/c/x86temps.c:172` sorts by **increasing raw temp size**, with floating-double alignment exceptions and an alias-offset case. Equal ordinary sizes have no ID tie comparison and inherit the current, potentially already-reordered list through the same unstable sort.

`SetTempLocation:144` grows `locals.size` and assigns a negative location. `AllocNewLocal` (`temps.c:357`) rounds each new allocation independently to `REG_SIZE` (four). Smaller objects therefore normally get allocated earlier at higher final ESP-relative addresses. In the eight-byte/twenty-byte array probe, the eight-byte object is at ESP+20 and the twenty-byte object at ESP+0, regardless of declaration order. A five-byte and eight-byte pair also respects raw size, even though both round to eight. Five and nine bytes reserve 20 bytes, not 16.

`ReUsableStack:149` scans newest stack entries first, accepts a sufficiently large existing slot only if none of its recorded inclusive instruction ranges overlaps, and does not split a larger slot. `AllocNewLocal:391` enters this path only if the temp has neither USE_IN_ANOTHER_BLOCK nor USE_ADDRESS and has a usable block ID. Address-taken locals get new storage; lexical scope ending is not sufficient evidence of reuse. Two disjoint scopes with a sixteen-byte array each still reserve 32 bytes in both profiles. Two disjoint sets of five named call-crossing scalars reserve **eight bytes**, using separate spill slots, despite non-overlapping source lifetimes. Do not infer that all dead source locals share storage.

`x86temps.c:49` can replace leading register-to-four-byte-temp moves with pushes when the cost model favors it; this has ordering and location prerequisites. `intel/c/x86base.c:76` (`AdjustBase`) can subsequently move the frame base to improve short displacement coverage. These paths were read but not separately triggered in this lane. They prevent interpreting a final frame offset as a simple declaration-number calculation outside the model's domain.

## 5. Physical-register passes after allocation

The final register encoding cannot always be attributed to the conflict allocator. `cg/c/generate.c:216` (`PostOptimize`) runs index construction/merging, peepholes, `Score`, dead-instruction removal, and optional scheduling after allocation. `cg/c/scins.c:199` (`TryRegOp`) can replace an operand with an equivalent older register; `TryOldIndex:155` can replace an address index. `ScoreMove:323` removes moves already known equal. Scheduling can then change instruction order without changing the home. These source facts are not an experimental isolation of which pass causes a particular game residue.

This is the boundary reached by the research: the source ranking is useful when the lowered names and references are known. In inlined, aliased, multi-block game functions, final disassembly does not uniquely reveal those inputs. The lane did not recover the complete original 10.6 IR or trace a specific allocator decision inside that compiler.

## Rejected hypotheses and stopping point

- Earlier declaration, earlier textual reference, lower TempId, and lower conflict bit are not interchangeable priorities. Scalar declaration reversal alone is already a measured negative; backend source explains why it can disappear before the final sort.
- “Stable descending sort with creation order as the tie breaker” is false for the read OW code and fails the structured mixed-benefit model. Implement the actual Shell sort if predicting such ties.
- “Always prefer caller-clobbered registers before creating a callee save” is too strong: the measured historical third leaf dword uses EBX with ECX free. “Prefer a newly available register over an old one” is also false in the reuse probe.
- Source lexical lifetime does not establish backend slot-reuse eligibility. Each needed byte temp can consume a four-byte slot; broadening or narrowing the C type can also change the lowered instructions, alias master, and conflict restrictions.
- Successful promotion of a two-field Pair in a minimal probe does not imply promotion of a context aggregate inside a large inlined caller. Help and pherc are direct counterexamples.
- Staging the coordinate arithmetic and widening/re-scoping the real Ramp color failed. The family stopped after six storage and four help forms, rather than adding dummy values or searching more scope permutations without a new prediction.
- The r2 factor-capture success remains a valid isolated source effect. This work does not retroactively claim an exact causal reconstruction of its 10.6 conflict graph from the descendant source.

The useful next evidence would be the **lowered conflict/name graph from 10.6**, or an independently recovered original inline/header context for one of the parked targets. In particular, a trace needs the ordered names, conflict list before/after sorting, computed savings, legal register list and CountRegMoves values, and spill masters before stack allocation. Final disassembly alone hides temporary elimination and register replacement. The checked-out OW source is read-only and is not the historical compiler, so no instrumented replacement compiler was substituted. The restricted model remains reproducible; a general predictive cure for the parked allocation cluster and a new STRICT unlock remain unfinished.
