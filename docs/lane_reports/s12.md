## Codegen facts and negative results

All measurements use pinned Watcom 10.6 C++, `plain-oe` (`-4s -s -bm -oe`) unless explicitly stated otherwise.

1. **Indexed destination versus pointer addition, isolated eight-way A/B.** In f_00441ec5, `memmove(&sortRows[j+1], &sortRows[j], ...)` independently scales `j+1`, reproducing the original. `sortRows+j+1` reuses the already calculated source address and makes the function 13 bytes shorter. `variants_sort_facts.txt`: both signed-level/indexed-destination choices are STRICT; all four pointer-addition choices are DIFF (198 diagnostic bytes). This extends the existing address-spelling observations to memmove arguments.
2. **Promoted byte comparison signedness, isolated in the same experiment.** An `int level` gives the original signed `jge`; `unsigned level` changes one byte to `jae`. With the correct indexed destination, the unsigned variants differ by exactly one byte. `sizeof(Choice)` versus literal `20L` for the byte count changes nothing in this isolated context; the earlier apparent arithmetic difference was not caused by sizeof signedness.
3. **Capture a repeated byte as a scalar before testing.** The eligibility helper needs `unsigned value=t->slots[i]; if(value) ...value...`; repeated direct member use keeps/reloads a pointer and widens at different places. This produces STRICT 004413e0 (118 bytes). The same capture after copying a slot makes 004422f0 STRICT (231 bytes); a bare byte field condition produced a later reload and a 259-byte function. Evidence: `try2.txt`, `try3.txt`, `try4.txt`, `try5.txt`.
4. **Keep the whole image-table pointer before element addressing.** WeaponControl::Draw is STRICT (343 bytes) with `MenuImages *images=gMenuImages; MenuImage *image=&images->images[index];`. Pre-offsetting to `gMenuImages->images` gives a 342-byte form with different load/LEA order. Evidence: `weapon_try2.txt`, `weapon_try3.txt`.
5. **Delay widening the weapon bit mask.** `U8 mask=actor->weapons; int bit=1<<i; int image=(mask&bit)?115:113;` gives the original byte load into DL, shift, then MOVZX into ESI. A direct condition or an inline byte-return accessor widens earlier. This removes all pre-epilogue differences in UpdateWeapons; it does not prove its unresolved shared tail. Evidence: `weapon_switch.txt`, `weapon_mask.txt`.
6. **By-value constructed coordinate argument applies the known EBP rule here.** Replacing a raw pointer to an aggregate point with a constructed GuiPoint passed by value creates the original EBP frame in UpdatePreview. Local allocation remains wrong (0x3c versus 0x44), so this is supported type/ABI evidence, not a match. `weapon_point_value.txt` and `variants_preview_point.txt`.
7. **Negative flag checks.** For all three candidates, explicit plain, -oe=80 and -oe=120 dry runs were performed to ask whether inline threshold choices explain the residuals. Movement and weapons retain the same STRICT sets. Inventory gains the validator in plain but loses the needed earlier inlining behavior. No profile sweep justified changing the final profile. See `first_plain.txt`, `first_oe80.txt`, `first_oe120.txt`, and `move_plain*.txt` / `weapon_plain*.txt`.
8. **Negative object-context checks.** Reference versus pointer eligibility and converting eligibility/discount helpers to GameSession methods did not repair inventory's frame/register decisions. Global Point setter/type variants canonicalized; no padding, dummy globals, inline assembly, byte code, or post-build patch was used.
