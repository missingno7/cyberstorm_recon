## What fixed the two functions (both are real source errors, not respellings)

- SimDrawBar (262 -> STRICT): in the original, the clip copy `viewportClipLeft = g4d381c;` comes BEFORE
  `long filled = value*width/maximum;`. The scheduler still moves the imul above the movsd, but `filled` now lives in
  ESI and `y` gets EBP (the old order kept `filled` across the copy and pushed `y` to memory, 368 B). The arrow index is
  one scalar `int arrow = image + 3 + (trend < 0);` (with the old `int down` capture: D58-60).
- HercBayOpen (144 -> STRICT): hercbay.c is compiled with `-oe`. HercBayOpen and HercBayReturnFromPurchase CALL the
  orphan HercBayAltStart (no callers); -oe inlines it, which produces the original parameter copies
  (`mov esi,ebx; mov edi,[ebp+18h]`), and the out-of-line copy stays where it is defined. AltStart ends with a call of
  the existing HercBaySetDisplay(). Open's second store is `closed` (+0x54), not `transition` (+0x50).
  Earlier lanes judged -oe "harmful" for hercbay; that judgement was made with the old source.

## Codegen facts (new evidence)

- In `-oxt` code, the order of a struct copy (movsd) and an arithmetic statement decides whether the result can live
  in ESI/EDI. The scheduler hides the source order (the imul is hoisted, the idiv is not), so read the idiv position.
- Orphan functions whose bodies appear, with parameter copies, inside other functions of the same TU mean that the TU
  is compiled with -oe and the callers call the orphan (hercbay.c).
- A dead `mov eax,reg` right after a null test, before reads through `reg`, is an inline receiver copy
  (f_00446570, PacketApply IsMoving). No spelling tried here reproduces it.
